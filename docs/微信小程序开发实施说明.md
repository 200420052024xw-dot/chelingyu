# 无人车共享运力平台微信小程序开发实施说明

> 本文件用于交给开发 AI 直接执行。阅读完成后应继续完成可运行的小程序原型，不要再次输出规划文档后停止。

## 1. 开发目标

在当前仓库中开发一个可通过微信开发者工具运行的原生微信小程序原型，完成普通用户下单、订单履约演示以及车辆所有者管理车辆的主要流程。

当前不接服务器、不接真实车辆、不接真实微信支付。所有数据通过本地 Mock 服务和微信本地存储运行，但页面、类型、服务边界与状态变化应按未来正式系统组织，便于以后替换为真实接口。

首版完成标准：首次启动可以看到地图首页，用户能够完整走通“查看附近运力 → 填写地址 → 填写货物 → 选择车型 → 确认订单 → 模拟支付 → 匹配车辆 → 配送完成”，同时可以从“我的”进入车辆管理、设置开放时间、查看任务和模拟收益。

## 2. 必读资料和优先级

开发前必须完整阅读：

1. `fronted_design/001.png` 至 `fronted_design/005.png`
2. `docs/无人车共享运力平台升级改造总体方案.md`
3. `architecture_design/README.md` 及其引用的全部文件
4. `data_design/README.md`、`data_design/types.ts`、`data_design/mock-data.ts` 和 `data_design/database-schema.md`
5. 本文件

发生冲突时按以下规则处理：

- **界面视觉和可见文案以 `fronted_design` 图片为最高依据。** 页面布局、主色、卡片层级、圆角、间距、按钮位置、底部导航、图标语义和图片中已有的文案均应优先还原。
- 业务定位、角色权责和价格边界以总体方案为准。
- 图片没有展示的页面和状态，按架构设计补全，并沿用图片的视觉语言。
- 数据字段和单位以修订后的 `data_design/types.ts` 为准。
- 本文件中的直接开发要求优先于较早架构文档中的实施建议。例如，原型图 004 的按钮保留“确认下单”，点击后进入图 005 的确认页面；不要自行改成“下一步”。

不得把整张原型图作为页面背景来伪装实现。页面必须由真实 WXML、WXSS、组件和本地数据组成，所有表单和按钮可交互。

## 3. 技术约束

| 项目 | 要求 |
|---|---|
| 客户端 | 原生微信小程序 |
| 语言 | TypeScript、WXML、WXSS、JSON |
| 工程目录 | 运行源码放在 `miniprogram/` |
| UI | 首版使用原生组件和自建组件，不依赖外部 UI 库 |
| 数据 | 本地 Mock 服务 + `wx.setStorageSync` / `wx.getStorageSync` |
| 地图 | 微信原生 `map` 组件、GCJ-02 坐标；距离、路线和 ETA 暂用 Mock |
| 支付 | 模拟成功、失败和取消，不调用真实支付 |
| 登录 | 默认演示用户，不要求真实手机号或微信登录 |
| AppID | 工程配置使用可替换的演示 AppID，并在 README 说明替换位置 |
| 后端 | 本期不创建云函数、数据库实例或服务器 |

所有服务接口保持异步。页面只调用 `services`，不得直接导入或修改 Mock 集合。地图、定位、存储、时钟和 ID 生成通过适配层封装。

## 4. 开发前先修订数据契约

在写页面前，先按 `architecture_design/04-rules.md` 修订 `data_design/types.ts` 和 `mock-data.ts`，至少完成：

- 把配送订单状态、支付状态和退款状态分开；正式订单从待支付开始。
- 增加预约等待状态、服务区域、草稿版本、报价输入摘要、订单价格快照和车辆时段预留。
- 增加车主共享开关，使其与平台启用、设备在线和运营状态分离。
- 补齐省、市、区和瑶湖校区服务区示例。
- 把“可下单场景”和“已有进行中订单场景”分开，保证同一辆车不会既可用又被订单占用。
- 统一订单、支付、调度事件的时间顺序，并为所有可调度车辆配置开放时段。
- 增加运行时校验函数，校验金额、时间、重量、尺寸、枚举和状态变化。

数据修订完成后再复制或引用到 `miniprogram/contracts/`。避免维护两套手写类型；可以通过同步脚本复制，并在 README 中说明源文件是 `data_design/types.ts`。

## 5. 前端视觉还原要求

### 5.1 总体风格

- 视觉基准是五张原型图片，不另行创造一套设计风格。
- 主色为图片中的高饱和绿色，正文使用深蓝黑色，辅助信息使用灰蓝色，警告/收件点使用红色，费用强调使用绿色。
- 页面背景为浅灰白，内容使用白色卡片、轻阴影和较大圆角。
- 底部主要按钮使用通栏绿色渐变或原型对应的绿色实色，保证文字清晰。
- 建立统一 WXSS 变量：颜色、字体层级、圆角、间距、阴影、底部安全区；不要在每页随意定义近似值。
- 使用 `rpx` 和安全区域适配 375～430 CSS 像素宽度的常见手机。不能按原图像素写死整页尺寸。
- 微信顶部胶囊、状态栏、滚动区域和底部固定操作栏不得重叠。

开发 AI 应直接打开原图检查细节，并在完成每个核心页面后与原图并排比较。还原优先关注：主要区块的位置与尺寸、留白、字体层级、颜色、圆角、按钮和卡片结构。地图供应商底图允许与效果图不同，地图上方与下方的业务覆盖层必须尽量一致。

### 5.2 图片资源

- 原型图仅作为视觉参考，不直接整图铺设。
- 车辆插图、车辆标记和必要图标如果没有独立资源，可从 AI 生成的原型图中裁切整理为本地原型资产，或制作风格一致的本地占位资源。
- 不使用不稳定的外部图片链接，不在页面中使用 emoji 代替主要业务图标。
- 所有资源放入 `miniprogram/assets/`，使用清晰命名；需要后续替换的资源记录在项目 README。

## 7. 必须实现的用户流程

### 7.1 用户下单

1. 首页加载瑶湖校区固定演示位置和附近车辆。
2. 点击车辆标记显示图 002 的车辆抽屉；点击空白区域恢复图 001 状态。
3. 点击“我要用车”创建或恢复当前用户的下单草稿。
4. 填写寄收地址，选择立即用车或预约时间。
5. 填写货物分类、说明、数量、重量、尺寸和特殊要求。
6. 系统根据货物和时段给出推荐车型；不适用车型展示原因，不能被选中。
7. 选择车型后生成带有效期的报价，进入图 005 确认页。
8. 修改地址、货物、时间或车型后，旧报价立即失效并重新计算。
9. “确认下单并支付”先幂等创建待支付订单，再打开模拟支付面板。
10. 支付成功后执行模拟匹配并进入订单详情；支付失败允许重试。

### 7.2 履约演示

订单详情显示地址、车辆、费用、支付/退款摘要和状态时间线。通过仅在 Mock 模式出现的“演示推进”入口依次推进：匹配成功、车辆前往取件、车辆到达、确认装货、配送中、到达收件点、确认收货、完成结算。

待支付、已支付但尚未装货的订单按规则允许取消。支付后的取消生成模拟退款；装货后不可直接取消，跳转客服。重复点击支付、收货或退款回调不得生成重复记录或收益。

### 7.3 车主流程

“我的”中展示“我的车辆”入口。演示用户兼具普通用户和车辆所有者身份，可以：

- 查看车辆位置、电量、续航、当前状态和当前任务。
- 绑定预置的未归属演示车辆。
- 开关是否共享给平台并编辑每周开放时段。
- 查看当前任务、历史任务以及待结算/已结算收益。

关闭共享不能破坏正在执行或已经承诺的预约。车主不能自主报价、直接向用户收款或任意修改订单状态。

## 8. Mock 服务与本地存储

建议目录与职责遵循 `architecture_design/01-system.md`：

```text
miniprogram/
  config/
  contracts/
  pages/
  packages/
  components/
  stores/
  services/
  implementations/mock/
  domain/
  repositories/
  adapters/
  view-models/
  fixtures/
  assets/
```

使用一个包含 `schemaVersion` 的本地数据库快照，保存用户、地址、车辆、规则、草稿、报价、订单、事件、支付、退款、车辆预留和分润。首次启动加载自洽种子数据；后续启动保留用户操作结果。设置页提供“重置演示数据”。

每次业务写入由服务层完成；涉及多个集合时先在内存副本中全部校验和更新，再一次写入。写入失败不得向用户显示成功。页面重新进入时读取权威快照，不把页面内对象当成长期数据源。

至少实现以下模拟场景：

- 正常下单并完成配送。
- 模拟支付失败后重试成功。
- 无可用车辆，支付后匹配失败并退款。
- 用户取消订单并退款。
- 预约配送和车辆时段冲突。
- 车辆电量不足或不符合货物能力。

## 9. 业务实现规则

- 金额以整数分保存；重量为克，距离为米，尺寸为毫米，容积为升，页面统一格式化显示。
- 用户选择的是车型能力偏好，最终具体车辆由调度服务匹配。
- 首页距离、车辆到取件点距离、配送路线距离是三个不同值，不能混用。
- 报价保存费用明细、总价、规则版本、草稿版本和有效期；页面提交的总金额不可信。
- 地址、货物、车型能力和价格在创建订单时保存快照，修改常用地址不得改变历史订单。
- 所有状态变化追加 `OrderStatusEvent`，不得只覆盖订单状态。
- 车辆可调度要求：平台启用、车主共享、设备在线、状态可用、位于服务区、开放时段覆盖任务、电量与能力满足要求、预约不冲突。
- “需要搬运”在首版提示暂不支持并阻止确认下单；不要默默忽略。
- 完成订单时只生成一次分润，金额之和必须等于可分配金额。
- 公共车辆 DTO 不暴露车主、设备号、结算账户等内部数据；车主任务只显示履约需要的信息。

详细规则以 `architecture_design/03-services.md` 和 `04-rules.md` 为准。

## 10. 交互、错误和隐私

所有页面必须有加载、空数据、错误和禁用状态。提交按钮请求期间显示忙碌并禁止重复操作。表单错误靠近字段展示，保留已经填写的内容。

定位默认使用固定演示位置，用户主动点击定位时再请求权限。拒绝权限后仍可继续使用演示位置。地图或定位失败提供重试与返回固定位置，不阻断整个原型。

演示联系人使用明确的虚构信息。界面列表中隐藏手机号中间位；内部原始测试值与展示脱敏值分开处理。不得记录或展示 OpenID、设备内部标识和结算账户。

客服按钮进入客服工单页面；消息红点由未读消息数据决定，不写死在 WXML 中。

## 11. 实施顺序

开发 AI 应持续完成以下工作，不在只搭骨架或只完成首页时停止：

1. 修订并校验数据契约和 Mock 场景。
2. 创建微信小程序 TypeScript 工程、主题变量、底部导航和本地存储。
3. 完成图 001～005 对应的核心下单链路。
4. 完成订单列表、订单详情、状态推进、取消和退款。
5. 完成我的车辆、开放时间、任务和收益。
6. 完成地址管理、消息、客服、设置和所有空/错状态。
7. 执行类型检查、规则测试和核心服务集成测试。
8. 使用微信开发者工具或可用的小程序构建工具验证工程，并逐页进行视觉检查。
9. 更新项目 README，写明打开方式、演示流程、模拟边界、AppID 替换位置和已知限制。

如果开发环境缺少微信开发者工具，仍要完成代码、静态检查和可执行的自动测试，并明确说明未完成的真机验证，不能用“无法打开 GUI”代替开发工作。

## 12. 验收标准

### 12.1 功能

- 图 001～005 的页面和跳转全部可用，表单数据能保留和修改。
- 可创建、支付、匹配、履约、完成、取消和退款订单。
- 订单列表、详情和时间线与本地数据一致，重启后仍能恢复。
- 车主开放时段会实际影响匹配，不是只有界面开关。
- 正常、失败、无车、冲突和权限拒绝场景都有明确结果。

### 12.2 视觉

- 首页、下单三步和确认页逐一对照对应原型图验收。
- 页面主结构、色彩、字体层级、间距、圆角、卡片、按钮和底部导航保持一致。
- 不出现明显的默认组件风格、随意 emoji、错位覆盖、文字截断或底部安全区遮挡。
- 未提供原图的页面看起来属于同一套产品。

### 12.3 工程质量

- 页面不直接修改 Mock 数据，不重复实现价格和状态规则。
- 无 TypeScript 类型错误，无明显控制台错误，无无效页面路径和缺失本地资源。
- 幂等、报价失效、状态迁移、时段冲突、退款与分润至少有自动测试。
- 代码中不包含真实密钥、真实支付参数或真实个人信息。

完成后应报告：已实现页面、核心演示路径、执行过的检查、未能执行的微信工具/真机验证，以及仍需替换的图片或配置。不要把计划中的功能描述成已完成。
