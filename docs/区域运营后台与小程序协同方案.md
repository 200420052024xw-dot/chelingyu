# 区域运营后台与小程序协同方案

> 状态：讨论稿，记录已确认的产品规则、现有实现差距和后续待定事项。本文是后续设计与实施的依据，不表示相关功能已经上线。
>
> 关联文档：[总体方案](./无人车共享运力平台升级改造总体方案.md)、[当前共享订单与运营后台运行说明](./共享订单与运营后台运行说明.md)。

## 一、目标与业务边界

平台以**区为最小运营单元、订单为业务主线、车辆为运力资源**。用户小程序提交需求并查看进度；车主小程序管理车辆开放时间、查看任务和收益；管理员后台负责区域运营、组织权限、订单处理、车辆准入、价格及模拟收益分配。三个端读取同一服务端业务状态。

本轮示例覆盖江西省南昌市，以及河北省唐山市的路北区、路南区。唐山先用两个区检验跨省区域切换和同城跨区调车；南昌和唐山各自在本市范围内接单、调车，暂不开放跨城市或跨省配送。南昌讨论中使用过“青山湖区”作为区域上下文示例，当前代码只初始化南昌县和东湖区；实际演示青山湖区须先由总部开通。

行政区是订单归属、价格、权限和收益的层级；接单能力还要经过路线可服务性及运力校验。唐山路北区、路南区按整个行政区受理地址，不再用一个圆形点位冒充整个区的范围。取送地址的行政区归属必须由服务端根据可信的坐标和区县编码复核，不能只相信小程序提交的区名。

## 二、管理员端产品结构

| 模块 | 主要工作 | 与其他端的连接 |
| --- | --- | --- |
| 区域运营台 | 选择总部、省、市、区上下文；查看指标及待办；下钻到订单或车辆 | 反映小程序订单、车主开放运力与履约事件 |
| 组织与账号 | 总部开通区域；建立省、市、区运营主体；为同一主体的多名员工分配岗位权限；维护长期合作联系人 | 决定谁能接收待办、查看数据、处理订单 |
| 订单运营 | 订单审核、自动派车结果、跨区协调、取货前改派、履约跟踪和异常结案 | 用户订单进度和车主任务来自同一订单事件 |
| 车辆资产 | 入驻审核、所有权、设备状态、开放时间、位置、任务和维护记录 | 车主设置共享与开放时段，设备适配层提供状态 |
| 收益结算 | 从区域汇总下钻到日期、订单、每个接收方的模拟分配和退款 | 车主收益页展示同一分配记录 |
| 价格规则 | 总部到省、市、区逐级授权；查看规则版本与变更记录 | 用户报价按取货区有效规则计算 |

**区域是全后台共享的视图上下文。**例如市级管理员进入“唐山市 → 路北区”后，订单、车辆、异常、收益和指标都使用路北区范围，不要求在每个模块重新选择区域。总部、省、市层级可以看辖区汇总并逐级下钻。切换视图不会改变账号身份；服务端始终按账号、岗位、区域和具体操作鉴权。

审核、派车、改派、履约和异常都属于订单生命周期，放在订单运营及订单详情中，不单设一套割裂的“调度中心”。运营台优先呈现可处理的待办，例如待人工审核、待市级协调、即将超时、取货前待改派、设备异常和已完成但尚未分配收益的订单；点击待办进入相应区域和业务对象。

区级处理本区日常业务；上级可介入辖区订单，但必须填写原因并留痕。价格只能在本账号所属层级及授权范围内修改；进入下级区域查看不产生下级身份或越级定价权。运营主体允许多名员工使用各自账号，至少区分组织管理、订单调度、车辆审核、财务查看和只读监督等岗位能力；具体岗位矩阵待细化。

## 三、区域开通、地址与报价

总部通过后台配置新省市区和区域接单范围，不能每开通一座城市就修改初始化代码。行政区域、运营主体、员工账号、有效价格、模拟分润规则和接单状态分别管理；**区域开放接单前，总部必须配置总体分润规则**。价格边界仍由总部 → 省 → 市 → 区逐级收窄。历史订单保留当时的价格和规则版本。

用户填写区内地址后，服务端复核取送点归属、是否同城，并调用腾讯地图路线规划：**地图能规划出路线，本版本先判为可达**，再继续运力校验和报价。地图明确查不到路线的需求进入**取货区支付前审核**：区级核实可行路线并记录依据，审核通过后重新生成报价供用户确认；仍不可达则结束未支付需求并告知原因。地图接口超时或报错属于“暂无法判断”，不能当成不可达结论；待重试或人工核实，确认前不进入支付。订单保留路线判断结果、时间和人工复核依据。小程序的地址文字和本地估价不作为服务端判定依据。

里程费通常按**腾讯地图规划路线距离**计算，不再按取送点直线距离计算。地图明确无整段路线、但取货区人工核实可通行时，由有审核权限的区级运营人员录入可计费路线里程、路线依据和审核理由，系统据此生成新报价，供用户确认后再支付；不得在付款后补录距离改价。用户确认并支付时锁定报价、计费距离、距离来源和价格规则版本；履约中绕行或故障后接力续送不自动追加里程费。异常订单仍按人工结案规则确定是否退款。

支付前还应检查同城是否有足够的、符合车型与货物、开放时段、在线健康状态、电量和预约冲突条件的不同车辆：单车需求至少 1 辆，多车需求至少达到所需辆数。车辆不必就在取货点附近；同城平台自有车也可参与。若支付前全城运力不足，不进入支付。报价按**取货区**价格规则计算；跨区调用车辆不改变用户已确认的价格。

## 四、单车订单与跨区调度

普通即时单优先在取货区自动匹配。单次预约、车型不适配、路线人工核实等情况进入相应的订单审核流程。支付后如本区无车，但同城其他区有合适车辆，订单进入市级跨区协调待办；市级确认调用其他区车辆并记录原因。上级介入后，取货区仍是订单服务归属区，车辆所属区和车辆所有权不改变。

支付后候选车辆可能被其他任务占用。进入协调的单车订单最多等待 **15 分钟**；到期仍未派车则结束订单并模拟全额退款。等待期间用户端显示“正在协调车辆”及剩余时间。车主端仅在实际派车后出现对应任务；用户端和车主端进入页面立即刷新，停留时定时刷新，关键节点保留通知能力。

取货前车辆故障可在原订单内改派，记录原车、新车、原因和操作人，并再次校验新车条件与占用。装货后故障或配送异常进入订单内的异常处理，不能立即把故障车及货物视作已正常释放。若仍需配送，由运营人员登记货物交接、原车与接续车辆、交接时间地点和经办人，建立关联的续送任务；用户仍面对原订单及原支付记录，不因换车再支付。人工结案支持确认完成、部分退款或全额退款，履约结果与退款金额分别记录并留痕；最终结案前不生成收益分配。发生续送时，车辆资产收益总额仍受总部规则约束，区级有结案权限的运营人员依据实际贡献填写原车与续送车之间的比例并说明理由；比例合计必须为 100%。本版本由该区级人员一人确认结案，无第二人审批；记录操作人、时间、退款金额、分配比例、理由和相关交接依据，结案后更正须保留原记录。

## 五、小程序多车配送与长期合作

小程序的“货物数量”继续表示货物件数，不等于车辆数量。自助多车需求限定为**同一取货点、同一目的地、同一时段，最多 5 辆**；不同路线可分别下单，若需统一协调多路线、超过 5 辆或长期固定运力，则使用“长期合作”联系入口。单车维持普通下单路径。

多车用户一次填写共同地址和时间，再填写各车承运的货物与车型需求；可复制上一车的信息。系统按每辆车校验适配性和同一时段的不同候选车辆，逐车报价并展示合计。用户**一次支付订单组合计**；后台形成一个便于汇总的订单组，每辆车对应独立的派车、履约、费用、异常和模拟分润记录。订单组金额等于子任务金额之和，部分退款能追溯到缺少的子任务。

若支付后暂时凑不齐全部车辆，系统保留已确认的候选运力并协调缺口，在整组确认前不让其中一辆提前出发。15 分钟协调期内，用户可随时选择接受当前已备齐车辆；接受后停止补车，派出已确认车辆并退还未提供车辆对应金额。到期仍未备齐时再给用户 **5 分钟**选择接受部分履约或取消整组；逾期未回应则整组取消、模拟全额退款。已开始履约的子任务发生异常时，按该任务单独结案。

小程序增加“长期合作”按钮，点击后只展示联系方式，不在此入口直接完成周期预约或支付。联系人按**所在区 → 市 → 省 → 总部**逐级查找，显示实际接洽团队。各级运营主体维护本级联系方式，变更需留痕；无真实可用联系方式时不显示演示号码。此入口与订单客服分开。

**本版本的长期合作到联系方式展示为止。**企业周期运力计划、容量预留、合同收费和月度结算均不进入本版本的后台或小程序。此前讨论过“预留容量、临近履约再派车”以及“按实际配送计费、按月汇总”的方向，留作后续版本讨论，不作为本版本的开发或验收要求。小规模临时用车继续通过普通订单或最多 5 辆的自助多车订单完成，每笔实际履约独立计费和分润。

## 六、车辆、收益与数据来源

车辆可调度状态由平台启用、车主共享与开放时段、设备在线与健康、电量、货物适配、当前位置、当前任务和预约冲突共同计算。管理员查看状态与不可调度原因，不手工填写“在线、健康、电量、位置”来冒充设备事实。本阶段通过统一演示设备适配层产生这些信号，页面明确标注演示；后续替换为真实设备接口。车主关闭共享或缩短开放时段只停止接新单，不撤销已经派出的任务；已承诺的预约也不能静默消失，需进入补车或协商流程。设备在线状态超过设定有效期未更新时，车辆退出新单候选池；已有派车产生运营预警，取货前可改派，装货后进入异常处理。信号有效期应由总部配置并在车辆详情显示最近上报时间。

用户向平台付款，订单完成后形成**模拟**收益分配，不表示真实打款。总部配置平台、省、市、区和车辆资产方的总体比例，区域开放前必须有有效规则。部分退款时以订单实收金额（支付减退款）作为分配基础，全额退款不产生该订单的可分配收入。车辆资产收益始终归实际车辆所有者：个人车归个人，运营商或平台自有车归对应持有人。跨区调车时，区级运营收益由取货区与出车区按总部配置比例分配，演示初始比例各 50%；同区完成时归同一区。每条分配记录保存订单、接收方、金额和规则版本，同一主体因运营与持车获得两种收益时分别记账。车主小程序收益页读取服务端的同一批分配记录。

## 七、南昌与唐山验收场景

1. **区域上下文与隔离**：总部能在江西、河北之间切换；河北省管理员只见河北辖区，唐山市管理员能从市级汇总下钻路北、路南；区级只操作本区。南昌示例使用同一套页面和权限规则。
2. **唐山跨区订单**：路北区取货、路南区送达，按路北价格报价；路北无车时唐山市级协调路南车辆，订单仍归路北；路北、路南按规则分享区级运营收益，资产收益归出车车辆的实际所有者。
3. **多车与部分履约**：路北用户同路线同时要 3 辆车，展示 3 笔任务及合计价格、一次支付；如最终只备齐 2 辆，用户可接受 2 辆并退还第 3 辆金额，已完成的 2 笔分别分润。
4. **路线可达性**：行政区内地址可提交需求；腾讯地图有路线则先按可达、按地图里程报价。明确无路线则由路北区在付款前复核；确认可通行时录入有依据的计费里程并向用户重新报价，审核未通过时用户不付款。地图接口故障时保持待核实。
5. **长期合作入口**：路北区未设置联系人时，显示唐山市级联系人；点击入口只展示联系方式，不创建预约或订单。
6. **装货后故障续送**：故障车的货物交接给另一辆符合条件的车，两车任务关联同一订单；用户不重复支付，人工结案后才确定退款与收益。

## 八、代码实施进度与主要差距

首批代码已实现总部在管理员端逐级创建省、市、区**区域档案**，并生成对应价格授权记录及创建留痕。新建档案默认为待开通，不进入小程序公开区域列表。管理员顶栏已有统一区域选择，总览、订单、车辆、入驻审核、通知、价格查询和账号列表按该区域读取数据；服务端会拒绝越权区域查询。查看下级价格为只读，仍只能修改自己账号层级的规则。各级管理员已能维护本级长期合作联系人；小程序按所在地行政区划代码逐级回退展示，无真实联系人时隐藏入口。服务端在配置地图密钥后会复核取送点行政区代码，按腾讯地图驾车路线里程报价；报价保存于服务端，订单创建时读取原报价并锁定里程和金额。模拟支付前再检查同城至少有一辆符合当前车型、开放时段、电量及预约条件的车；无车时不扣款。地图失败暂停报价；明确无路线时生成取货区支付前核实订单，区级填写人工计费里程、通行依据和审核理由，用户确认新报价后才能支付。当前尚不能把唐山路北、路南视为已开放接单区域；接单范围、完整分润规则与运力仍需配置。

当前支付、退款、位置和车辆绑定仍为演示能力；真实微信支付、设备接入和实际资金打款不属于本轮已确认的模拟闭环。现有 PostgreSQL 以一行 JSONB 保存共享状态，扩展多城、多车和账务时需要规划独立实体与数据迁移；总部新建的区域档案会保存到当前状态中，但不会自动形成行政区服务边界和可调度车辆。企业周期预约的数据类型草稿可以保留，但本版本不接入业务流程。

## 九、下一轮待讨论

1. 装货后异常的部分退款计算依据、货损与服务完成程度如何记录，以及结案后更正的操作边界。
2. 车辆信号有效期的默认时长，以及人工录入路线依据的标准字段。
3. 员工岗位的具体权限矩阵、总部总体分润比例与运营指标计算口径。
4. 多车同单混合车型与货物分配的页面细节，以及长期合作联系方式的实际数据录入。

## 十、建议实施顺序

1. **区域基础**：总部区域档案、统一区域上下文、权限校验及长期合作联系人已完成；下一步补行政区服务范围和开通条件。
2. **可下单闭环**：服务端可信地址归属、腾讯地图路线与里程报价、支付前运力数量校验，再接本区优先与市级跨区协调。
3. **多车与异常**：订单组、一次支付、部分履约选择、取货前改派、装货后交接续送和人工结案。
4. **逐单收益**：总部比例配置、订单分配明细及车主小程序同源收益；补足员工岗位权限与运营指标。

上述顺序是开发安排，不改变前文已确认的业务规则；每阶段均需分别验收南昌与唐山场景。
