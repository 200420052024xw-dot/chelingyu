# 系统分层与工程结构

## 当前运行结构

```text
页面 / 业务组件
       ↓ 调用、展示结果
页面状态 / 下单草稿状态
       ↓
异步服务契约 services
       ↓ 由启动配置选择实现
Mock 服务：校验、计价、匹配、状态迁移
       ↓
Repository：统一读写本地数据快照
       ↓
微信本地存储

地图、定位、时钟、ID、存储通过 adapters 封装
```

页面不直接修改车辆、订单或支付集合；全部操作经由服务完成。服务返回独立数据副本，防止页面修改对象时意外改动存储。一次业务命令对订单、支付、车辆、事件的修改一起提交。

## 职责分配

| 层 | 负责 | 不承担 |
|---|---|---|
| pages | 用户输入、导航、加载/错误/空状态 | 计价、判断订单是否可跳状态 |
| components | 可复用展示和交互，向上发出事件 | 全局数据写入 |
| stores | 会话、选定区域、下单草稿等跨页临时状态 | 权威订单列表和车辆副本 |
| services | 稳定接口、业务命令、查询结果 | 页面布局 |
| mock/domain | 模拟定价、调度、权限检查、订单状态机 | 直接调用页面 API |
| repositories | 查询和保存数据、版本迁移 | 用户提示文案 |
| adapters | 微信能力、时钟与外部系统接入 | 业务决策 |
| view-models | 金额、状态、按钮、列表卡片的展示转换 | 重新计算应付价格 |

## 计划工程结构

保留现有设计目录；未来工程采用根目录配置、`miniprogram` 为运行源码目录。下列文件均为计划路径，尚未生成。

  packages/owner/pages/     车辆、任务、收益
  packages/account/pages/   消息、客服、设置
  components/               运力卡、地址卡、费用表、状态时间线
  stores/                   session、region、order-draft

共享组件和服务放主包；分包不相互引用页面内部代码。创建工程时验证原生工具链的编译、分包与组件构建流程，不预先锁定未验证的版本。

## 本地数据和生命周期

- 用一个带 `schemaVersion` 的本地数据快照存放业务集合，跨实体变更通过串行命令队列处理，计算成功后一次写入；写入失败不展示成功。
- 使用 `cly:prototype:v1:db` 等命名空间，避免与其他缓存混用。只在首次启动或用户明确重置演示数据时加载种子。
- 草稿单独保存 `draftId`、`revision`、`updatedAt`。重新打开可恢复；成功创建订单后清理对应草稿。
- 本地存储无法读取或版本无法迁移时给出恢复/重置入口，不静默覆盖用户数据。
- 页面隐藏时停止刷新、解除订阅。重新进入页面查询权威快照，避免多页各保存一份订单后互相覆盖。
- 默认通过演示面板显式推进车辆状态；预约演示使用可控时钟。不要依赖后台定时器持续运行。
- 真定位拒绝时可选择演示地点；地址选点支持固定地点列表作为回退。路线和 ETA 模拟值要有演示标识，不伪装成真实导航。

## 未来接入路径

将服务入口由 Mock 实现切换为远端实现，保留页面调用签名。正式服务端负责身份鉴别、区域权限、报价复算、车锁/预约冲突、支付回调和资金账本；前端只展示结果。远端实现负责把传输格式转成页面 DTO。

初期后端可采用一个模块化应用，内部仍按用户、车辆、订单、价格和结算划分。管理后台通过相同后端按组织范围访问；车辆网关接收设备状态并驱动履约事件。地图密钥配置、微信登录、支付接入和域名要求在实际接入时核对官方文档。
