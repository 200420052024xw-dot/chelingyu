# 业务规则与状态变化

## 订单、支付和退款独立

现有 `OrderStatus` 混入 `refunding/refunded`，会使“订单已经取消”在退款过程中消失。实施前调整为三个状态维度：订单状态描述履约；Payment 描述收款；Refund 描述退款。列表“已取消”仍展示取消订单，并另标退款进度。

草稿的 `draft/quoted` 只属于草稿阶段；正式订单从 `pending_payment` 开始。

| 原状态 | 触发 | 新状态 | 一并变更 |
|---|---|---|---|
| pending_payment | 模拟支付成功 | paid | 支付成功记录、支付事件 |
| paid | 即时调度 | matching | 候选车辆记录 |
| paid | 预约预留成功 | scheduled（待新增） | 有明确开始/结束时间的车辆预留 |
| scheduled | 到预约调度时刻 | matching | 验证预留车辆；原型以演示时钟触发 |
| matching | 成功分配 | dispatched | 原子占用车辆、分配记录 |
| dispatched | 车辆启程 | vehicle_to_pickup | 车辆状态与任务引用 |
| vehicle_to_pickup | 车辆到达 | awaiting_loading | 到取件点事件 |
| awaiting_loading | 确认装货 | delivering | 记录实际取件时间 |
| delivering | 车辆到收件点 | arrived | 到达事件，保留占用直到卸货完成 |
| arrived | 确认收货 | completed | 实际交付时间、释放车辆、生成一次分润 |
| pending_payment | 用户取消/支付超时 | cancelled | 关闭未支付单 |
| paid / scheduled / matching / dispatched / vehicle_to_pickup | 允许取消 | cancelled | 释放未执行预留/占用，创建退款 |
| matching | 无容量 | failed | 失败原因、释放资源、创建退款 |

装货后异常通过工单处理，不允许用户直接把车辆释放给下一单。执行中故障保留现场状态并记录异常，后续由平台处理。取消中的车辆释放只在停止任务确认后生效；Mock 可把停止确认作为同一次模拟命令的一部分。

订单事件追加保存；禁止通过页面传任意目标状态。允许操作来自服务端规则。重复收货、支付回调或退款回调返回已有结果，不能重复生成收入。

## 车辆、时间和调度

- “共享开关”“设备在线”“运营状态”“是否在开放时段”是独立条件，不能仅凭 `status=available` 决定接单。
- 开放时段按 Asia/Shanghai 解释，周一为 1；区间采用左闭右开。跨午夜在保存时拆成两天时段；禁止重叠区间。
- 开放窗口需覆盖预计取件、装卸、配送和缓冲全程。预计结束超出开放时间时，不参与候选。
- 增加预留记录 `VehicleReservation`：车辆、订单、开始、结束、状态；同车活动预留不得重叠，不能仅用车辆的 `reserved` 状态表达全部未来预约。
- 模拟调度先筛区域/设备/能力/开放窗口/预约，再按距取件点的距离排序，ID 作为稳定次序。定位缺失、过期或电量不足应明确排除。
- 用户地点到车辆的距离用于首页；车辆到取件点的距离用于调度；取件点到收件点的路线距离用于计费，三者不能混用。
- 演示计算使用固定路线和 ETA，真实道路通行规则、路线可达性和电耗预测留给正式车辆系统。

## 货物与价格

- 数量为正整数；重量、尺寸有值时必须为正整数。缺少重量/尺寸时引导补充，不把“未知”当作 0 并声称一定适配。
- 总重量为数量 × 单件重量；同规格货物体积按尺寸计算。容积够不代表最长边可放入；缺少货厢尺寸时只做初步推荐。
- 冷链需同时检查温控能力与温度范围；首版没有相关参数的车辆不得承诺具体温度。
- 报价示例：基础费 500 分，里程 1300 米，每公里 200 分，里程费四舍五入到分为 260，总价 760 分。
- 最终报价受有效省市区价格边界约束；超上限不静默收费，按规则限价或返回不可报价，本原型采用返回不可报价；低于最低价补齐并在明细列出最低收费调整。
- 上级收窄价格范围后，下级越界规则不得继续产生新报价，需重新审核调整；已接受订单价格不变。
- 分润按订单锁定的规则版本计算。比例之和为 10000；各项先取整，余分按小数余数从大到小分配，同余按固定参与方顺序，合计精确等于可分配金额。
- 原型只在完成订单后形成模拟分润；后续真实退款需要负向冲销流水及资金账本，不修改历史收入伪装从未发生。

## 已有数据契约的实施前修订清单

现有数据文件为初稿，本次不直接改写它们。以下修订必须在使用 Mock 编写页面之前完成并通过校验：

| 问题 | 修订 |
|---|---|
| 校区 `region_yaohu` 无对应行政实体 | 新增 ServiceArea；补齐省市区与关联示例 |
| 车辆可用，但示例订单已经占用该车 | 拆为“新用户下单”与“进行中订单”两个自洽场景 |
| 事件早于订单 createdAt | 统一订单、支付、事件时间线 |
| 只有一辆车配置开放规则 | 所有可调度车辆必须有有效授权和开放规则 |
| 报价只绑定 draftKey | 增加草稿版本、输入摘要和服务区域；绑定输入不可被页面修改 |
| 金额只有订单总额与报价引用 | 订单保存不可变价格明细和规则版本快照 |
| 企业包时段被混成配送订单 | 独立 CapacityReservation 与 occurrence/预约实例；每次配送可关联实例 |
| 退款混在订单主状态 | 拆开履约、支付和退款状态，补预约等待状态 |
| 资产启用和共享授权混淆 | 增加车主共享开关，保留平台启停权限 |
| 时间、金额别名没有运行时约束 | 增加日期/时间/整数范围/枚举校验；类型检查不能替代输入校验 |
| 模拟图片路径没有实际文件 | 准备资产或明确占位图再接入页面 |
| 示例坐标未经校验、缺少坐标体系 | 地图点位统一标明 GCJ-02；演示坐标与真实校区分开，核实后再标真实地址 |
| 脱敏电话位于可编辑原始字段 | 原始测试值与展示脱敏字段分开，测试值仅作虚构数据 |

对外接口不返回 OpenID、设备标识、结算账户和全量审计。Mock 的本地角色检查用于演示一致性，不代表生产环境安全边界。
